# 构建与后续维护

## 版本与来源

`configs/build-lock.json` 固定 OpenWrt、官方 feeds、PassWall2 和其依赖 feed 的完整提交。GitHub Actions 同样固定完整提交。新版本需要显式修改锁、检查相应安全公告和变更，再编译测试。

首版基线为 OpenWrt 25.12.6，项目版本 0.1.0-rc1，PassWall2 发布标签 26.11.11-1 的对应提交。版本信息按本次取证日期记录，不代表未来最新版本。

官方源以发行 tag 内的 feeds 锁为基础，使用 GitHub 上游镜像；只安装已选择的包配方及其依赖，不把所有无关应用加入 Kconfig，避免无关包的依赖环影响配置。`make defconfig` 后必须检查配置，没有某项必需功能就失败，不把缺插件镜像当作成功成品。

自编译包与内核依赖必须配套保存。不要强行安装另一固件的 kmod，禁止忽略签名或依赖错误。软件包索引及架构与安装的发行版必须匹配；官方仓库更新不保证保留自编译内核所需 ABI。

## 云端环境

- Ubuntu 24.04 标准 GitHub 托管 Linux 运行器，单任务最多 350 分钟，编译并行度 3。
- 最少 30GiB 空闲磁盘、6GiB 内存。运行器不满足条件即明确失败，不清除宿主工具来凑空间；可改用更大的运行器或独立 Linux 构建机。
- 云端接入 Ubuntu 官方源；本地需要依赖时优先大陆可信镜像。镜像不改变源码锁和哈希校验。
- 不使用高权限 GitHub Token，不请求写仓库或发布权限；工作流仅 `contents: read`，手动启动完整编译。
- 构建不会读取个人旧配置，更不会访问局域网群晖。发布、刷机是独立动作。

## 产物

成功构建需同时存在 Legacy 和 UEFI 的 SquashFS 完整磁盘镜像，且 manifest 包含全部必需软件。镜像文件含项目版本号。

- 固件包：镜像、SHA256SUMS、软件 manifest、resolved.config、diffconfig、实际 feeds 提交、验证边界说明。
- 扩展包：本次编译的离线包和索引、SDK/Image Builder（构建成功产生时）、锁定配置和校验文件。
- 诊断：完整日志与解析后的配置，失败时也尽量上传。不要向构建脚本注入私人凭据，否则日志可能含敏感值。

GitHub Artifact 到期会由平台按保留策略清理；用户应下载保存到版本目录。工程本身没有删除旧发布的操作。

源码对应关系通过构建锁及项目公开提交记录保存。对分发二进制所需的完整对应源码，应保留上游源码和补丁，并遵守相应许可证；公开发布正式固件前补齐源码归档，当前 workflow 仅输出候选构建 Artifact。

## 失败处理

检查 diagnostics 的日志定位到具体包、源下载或空间失败。修改锁定输入、依赖或构建参数后新建一次 run；同版本源不能静默漂移。失败不自动更换到 Snapshot，不偷偷移除必需包，不把单线程重试的成功当作所有错误已解释。
